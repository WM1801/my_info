=== Основы
`System call` - обращение из кода програмы к системной функуции, к то му что называют системным именем system kernel symvol.

Первоначально в программировании под понятием _символ_ - понималось имя функции. 

То есть  system call - вызов функции из ядра (пример: Open(), close(), read(), write())

*Пользовательская программа* - то есть я могу только пользоваться *system call*. 

*Системная программа* - то есть я могу только пользоваться *system call* и создавать свои. 

Демон - пользовательский код, так как только вызывает системные вызовы. 

Написание драйверов создание новых системных вызовов. Для этого в Linux есть понятие модуля ядра (драйвер). 

Связь пользовательского по с устройством:
*device - IRQ - module - daemon - user*. 
Драйвером можно считать связку *IRQ - module - daemon*.

`module` - исходный код, текст программы,  который реализует логику передачи данных от оборудования (виртуального или реального) пользователю. Модуль должен котнтролировать процес подключения программы к устройству. 


*Виды устройств:*

* Символьные устройства (90%)

* Блочные устройства (диски), отличается от символьнгого. Другие права доступа и блочное устройство может сообщать системе информациб о геометрии диска(Цилиндры и тд). 

* Сетевые интерфейсы. Для реализации сетевого интерфейса нужна сетевая железка. 

* SCSI device

Взаимодействия с устройством происходит через файлы устройств. 

*Ключевые директории:*

. /dev

. /proc - служебная инфо о модуле

. /sys - можно задать параметры модулей 


*/proc/devices* - прочитав который можно увидеть мписок устройств в нашей системе.

=== Системный лог 
Системный лог находится: _/var/log/_. Посмотреть можно _tail -f /var/log/kern.log_. 
Из модуля ядра нет возможности обратиться к вводу-выводу, потому что kernel не видит стандартных терминалов. На самом деле, модуль ядра может осуществлять ввод-вывод, но механизмы кардинально отличаются от тех, к которым мы привыкли в пользовательском пространстве (user-space).

*Почему в ядре нет "стандартных терминалов"?*

Понятия _stdin_, _stdout_, _stderr_ и функции вроде _printf()_ или _scanf()_ — это абстракции стандартной библиотеки C (glibc). Они работают только в пользовательском пространстве. Ядро операционной системы работает на более низком уровне:

* Оно не привязано к какому-то одному "текущему" терминалу или процессу (оно обслуживает их все).

* Оно может выполнять код до того, как пользовательское пространство и файловые системы вообще инициализированы.

* У ядра нет своего "контекста выполнения" с открытыми файловыми дескрипторами по умолчанию, как у обычной программы.

*Как же тогда делать ввод-вывод из модуля ядра?*

В зависимости от твоей задачи, в арсенале разработчика ядра есть несколько основных механизмов:

. *printk (Логирование и отладка)*
+
Это прямой аналог printf для ядра. Вместо вывода на экран, printk записывает сообщения в кольцевой буфер ядра _(kernel ring buffer)_.
Как прочитать: Из пользовательского пространства ты можешь увидеть эти сообщения с помощью команд _dmesg_ или _journalctl -k_.
Пример:_ printk(KERN_INFO "My module: Hello, World!\n")_;
+
. *Символьные устройства (Character Devices)*
+
Это стандартный и правильный способ двустороннего обмена данными между модулем ядра и пользовательской программой.
Модуль регистрирует устройство (например, _/dev/my_device_).
Пользовательская программа открывает этот файл и использует обычные системные вызовы _read()_, _write()_, _ioctl()_.
Ядро перехватывает эти вызовы через структуру file_operations, которую ты реализовал в модуле.
+
. *Виртуальные файловые системы: procfs (/proc) и sysfs (/sys)*
+
Отличный способ для экспорта статуса модуля или приема простых настроек.
_Sysfs_: Идеально для атрибутов устройств и драйверов (например, изменить значение переменной модуля через _echo 1 > /sys/class/my_class/my_device/enable_).
_Procfs:_ Исторически использовался для вывода информации о процессах и ядре, сейчас чаще используется _sysfs_, но _procfs_ все еще применяется для специфичных задач.
+
. *Netlink-сокеты*
+
Если тебе нужен сложный, асинхронный и надежный обмен сообщениями между ядром и пользовательским пространством (например, для сетевых подсистем или правил брандмауэра), используется семейство сокетов _AF_NETLINK_.
+
. *Прямой ввод-вывод в файлы из ядра (Advanced / Rare)*
+
Технически ядро может открывать файлы на диске с помощью _filp_open()_ и читать/писать в них через _kernel_read() / kernel_write()_.

NOTE: *Важно: Это считается плохой практикой для обычных модулей. Ядро не должно зависеть от пользовательских файловых систем для своей основной работы. Этот механизм используется только в очень специфичных случаях (например, механизмы трассировки ftrace, запись дампов памяти при панике ядра kdump или некоторые подсистемы аудита).*

*Резюме для обучения:*

* Не пытайся "заставить" ядро писать в стандартный вывод. 

* Вместо этого задай себе вопрос: "Кто и как должен получить эти данные?"

* Если это просто отладка → используй printk.

* Если данные должна читать пользовательская программа → создавай символьное устройство _(/dev/..._) или интерфейс в _sysfs_.
