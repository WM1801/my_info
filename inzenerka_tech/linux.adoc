== makefile
Включает в себя: 

* Цель
* Требование 
* Команда (перед команой ставится табуляция)

Коментарии обозначаются через `#`

[makefile, shell]
----
# коментарий 
#с подключением статической библиотеки
#hello example makefile 

hello: main.o libhello.a
	gcc -o hello main.o -L. -lhello

main.o: main.c
	gcc main.c -c

libhello.a : hello.o goodbye.o
	ar cr libhello.a hello.o goodbye.o

hello.o: ../library/static/hello.c
	gcc -I../library/static -c ../library/static/hello.c 

goodbye.o: ../library/static/goodbye.c
	gcc -I../library/static -c ../library/static/goodbye.c 


clean: 
	rm -f *.o *a hello
----

[makefile, shell]
----
# коментарий 
#с подключением динамической библиотеки

#hello example makefile 

hello: main.o libhello.so
	gcc -o hello main.o -L. -lhello -Wl,-rpath,.
#	rm -f *.o

main.o: main.c
	gcc main.c -c

libhello.so : hello.o goodbye.o
	gcc -shared -o libhello.so hello.o goodbye.o 

hello.o: ../library/static/hello.c
	gcc -I../library/static -c ../library/static/hello.c -fPIC

goodbye.o: ../library/static/goodbye.c
	gcc -I../library/static -c ../library/static/goodbye.c -fPIC


clean: 
	rm -f *.o *so hello
----

== Окружение 
*`Окружение`* - набор пар (переменная = значение), которые доступны каждому пользовательскому процессу. Название `environ`. 

При запуске родительский процесс передаёт копию окружения дочернему, который может делать со своей копией, все что угодно. Это не повлияет на работу системы в целом. В линукс есть несколько способов взаимодествия с переменными окружения из процессов. 

Есть библиотека `unistd.h` все необходимые базовые объявления для работы в линукс. Внутри этой библиотеки есть массив envirement который хранит построчно список переменных и значений.

== IPC Межпроцессное взаимодействие

Инструменты линукс обеспечивающее передачу информации между процессами операционной системы. 

Проблемы монолита

* долгая загрузка
* сложность изменения
* влияние ошибок более серьезно 
* тяжело передавать и выводить информацию 

=== Pipe

==== Неименованный канал
Самый распространенный вариант внутри программной передачи данных. 
Программа запускает из себя другую программму как процесс и следит за тем что она ей передаст. При этом мы можем использовать вывод другой программы вообще не вдаваясь как она создана. 
За работу неименованного канала отвечает popen() pclose(). При этом при использовании неименованного канала мы передаем информацию в одну сторону. 

Если нужна передача в обратную сторону то нужна другая концепция fork(). При этом применяются два канала связи, это будут файлы, это будут потоки данных в оперативной памяти. Где один процесс читает, а другой пишет. 
pipe() - создает два неименованных однонаправленых канала. Уних два дескриптора.  

Особенности:

* Создаются во время исполнения программы.
* Существуют в оперативной памяти.
* Не имеют имени в файловой системе.
* Однонаправленные: один процесс пишет, второй — читает.
* Используются через вызовы pipe(), popen(), fork(), read(), write()


Пример: popen() и fread
Функция popen() запускает внешнюю команду и открывает поток, по которому можно получить ее вывод. Это упрощает чтение результата других программ.
[c, code]
----
FILE* f = popen("ls", "r");
fread(...);
pclose(f);
----
Недостаток popen() — она запускает команду через shell, что может быть неэффективно и небезопасно.

==== pipe() + fork()
Функция pipe(int fd[2]) создает два файловых дескриптора:
fd[0] — для чтения;
fd[1] — для записи.
Далее вызывается fork(), который создает копию процесса. После этого каждый из процессов (родительский и дочерний) может использовать пайп для обмена данными.

----
int pipefd[2];
pipe(pipefd);
pid_t pid = fork();

if (pid == 0) {
    // дочерний процесс: читает
    close(pipefd[1]);
    read(pipefd[0], ...);
} else {
    // родительский процесс: пишет
    close(pipefd[0]);
    write(pipefd[1], ...);
}
----

=== Именнованный канал 
Когда нужно, чтобы разные программы (а не процессы одной программы) взаимодействовали между собой, используют именованные каналы — FIFO-файлы.

`mkfifo()`
Создает файл специального типа в файловой системе:
----
mkfifo("myfifo", 0666);
----

Далее обычные вызовы fopen, fprintf, fgets позволяют писать и читать данные.
Важно: unlink("myfifo") удаляет канал после использования, но только если в нем нет данных.


*Особенности реализации*

* Неименованные каналы — это временные, процессо-локальные средства связи.
* Именованные каналы — постоянные, видимые в файловой системе.
* popen() удобно использовать для чтения вывода утилит.
* execve() — для замены процесса другой программой.
* fork() — создает новые процессы.
* pipe() — соединяет процессы очередью (FIFO).
* dup2() — перенаправляет стандартные потоки.


Ключевые функции
|===
|Функция|Назначение
|popen()|Открыть поток к внешней программе
|pipe()|Создать неименованный канал
|fork()|Создать дочерний процесс
|execve()|Заменить процесс другим
|mkfifo()|Создать именованный канал (FIFO)
|read()|Считать данные из дескриптора
|write()|Записать данные в дескриптор
|dup2()|Перенаправить один поток в другой
|unlink()|Удалить файл или канал
|===


== Очередь сообщений
`Очереди сообщений` — один из механизмов межпроцессного взаимодействия (IPC) в Linux наряду с пайпами (pipe) и разделяемой памятью (shared memory). В отличие от пайпов, которые появились с самого начала существования Unix, очереди сообщений были введены позже, как часть System V IPC, чтобы обеспечить:
удобную и системно-управляемую передачу данных между процессами;
поддержку обмена структурированной информацией (а не просто потоками байтов);
произвольный доступ к сообщениям внутри очереди (в отличие от строго FIFO-пайпов);
идентификацию сообщений и возможность приоритизации.

*Как работают очереди сообщений?*

*Общие принципы:*

* Очередь создается в системе и управляется ядром ОС.
* Для доступа к очереди используется уникальный ключ (key_t), который известен всем взаимодействующим процессам.
Ключ может быть сгенерирован вручную (например, 1174) или автоматически через вызов ftok(path, id), основанный на пути к исполняемому файлу.
* Каждое сообщение имеет обязательное поле long mtype, определяющее его тип/приоритет.
* Структура сообщения может быть произвольной (любые данные), но обязательно начинается с long.

*Основные системные вызовы*
|===
|Вызов|
Назначение
|msgget()|Получение или создание очереди
|msgsnd()|Отправка сообщения в очередь
|msgrcv()|Чтение сообщения из очереди
|msgctl()|Управляющие операции: удаление очереди, получение статуса и др.
|===


*Особенности работы с сообщениями*

*1. Извлечение сообщений по типу*

Поле mtype можно использовать для выбора сообщений:

* больше 0 — получить первое сообщение указанного типа;
* равно 0 — получить первое сообщение любого типа (FIFO);
* меньше 0 — получить сообщение с mtype <= abs(mtype).
Это позволяет реализовать приоритизацию, обработку системных и пользовательских событий, контроль очередности и т.п.

*2. Передача данных*

* Сообщение — это последовательность байтов, которую передает один процесс другому.
* Если структура неизвестна, сообщение интерпретировать невозможно.
* Требуется общая библиотека структур на клиенте и сервере (например, Request, Response).
* Возможны проблемы выравнивания памяти — поля должны быть кратны 4 байтам.
* Для передачи используют буферы размером страницы памяти (обычно 4 КБ).
* Для проверки целостности можно использовать контрольные суммы и пакеты (buffer + checksum).


*Свойства очередей сообщений*

* Сообщения хранятся в очереди до чтения. Поддерживается накопление.
* Очередь должна быть удалена владельцем после использования — иначе произойдет утечка ресурсов.
* Произвольная структура сообщений, но максимальный размер:
    ** ~8 КБ на 32-битных системах;
    ** ~16K сообщений на очередь (зависит от ядра).

*Сравнение с другими IPC-инструментами*
|===
|Механизм|Направление|Буферизация|Передача структур|Очередность|Произвольный доступ
|Pipe|Однонаправленный|Есть|Нет (байты)|FIFO|Нет
|Shared Memory|Двунаправленный|Нет|Да|Нет|Да (но вручную)
|Message Queue|Двунаправленный|Есть|Да (структуры)|FIFO/по mtype|Да
|===

*Архитектурные замечания*

* Для полноценного отклика на события (например, из GUI), приложения реализуют цикл событий (event loop).
* Обработчики событий (handlers) должны быть реализованы как функции или методы классов.
* Важно избегать блокировок в этих обработчиках — иначе ОС решит, что программа не отвечает.

*Пример: простой чат на message queue*

* Сервер и клиент обмениваются структурированными сообщениями через одну очередь.
* Используются типы сообщений: 1 — от клиента, 2 — от сервера.
* Структура:
----
struct message {
    long mtype;
    pid_t sender_pid;
    char text[256];
};
----

*Сценарий:*

* Клиент отправляет сообщение → Сервер читает → отправляет OK в ответ.
* Возможна реализация более сложных схем: "радио"-чат, приоритизация и т.п.

*Практические советы*

* Никогда не забывайте вызывать msgctl(..., IPC_RMID, ...) — иначе очередь зависнет.
* Размер сообщения всегда рассчитывайте как sizeof(msg) - sizeof(long) — т.к. mtype обрабатывается системой отдельно.
* В качестве key_t предпочтительнее использовать ftok(), а не вручную выбранные числа.
* Используйте IPC_CREAT | IPC_EXCL, чтобы избежать конфликта при создании уже существующей очереди.
* Следите за буферизацией — возможны тайминговые баги, особенно в системах реального времени.


== Shared Memory

*Shared Memory* — это механизм взаимодействия между процессами (IPC), позволяющий нескольким процессам работать с одним и тем же участком оперативной памяти. Это один из самых быстрых способов обмена данными между процессами, так как не требует копирования данных из одного адресного пространства в другое.

=== Почему не "разделяемая память"?

В русской литературе часто используется термин "разделяемая память", но он может вводить в заблуждение: "разделенная" память может означать совершенно другое (например, NUMA-архитектуры, где у каждого процессора свой блок ОЗУ). Поэтому английский термин shared memory — более точный и нейтральный.

=== Можно ли обратиться к чужой памяти?

* Нет. В нормальных условиях процесс не может напрямую обращаться к памяти другого процесса.
* У каждого процесса свое адресное пространство.
* Любая попытка обращаться к "чужой" памяти считается нарушением и расценивается как хак или эксплойт.

=== Виды памяти (с точки зрения процесса)
* Своя память — инструкции и переменные текущего процесса.
* Чужая память — все, что принадлежит другим процессам или ядру.
* Куча (heap) — динамически выделяемая память, которую процесс сам запрашивает и освобождает.

=== Как работает Shared Memory?

1. Память выделяется при помощи системного вызова shmget.
2. Отображается в адресное пространство процесса вызовом shmat.
3. Для корректной работы требуется согласованность действий между процессами (например, кто и когда читает или пишет).

*Пример: два процесса и переменная x*

Допустим, x = 0. Два процесса одновременно выполняют x++.
Возможные значения:

* Идеально: x = 2.
* На практике: может быть 1 или даже 0.

Почему?

* x++ не атомарная операция.
* Процессы могут "переписать" друг друга.

=== Проблема синхронизации

При одновременной работе с памятью:

* *Чтение + запись:* возможны "битые" данные.
* *Запись + запись:* конфликт, потеря данных.
* *Чтение + чтение:* безопасно.

Вывод: *необходим механизм синхронизации*.

=== Семафоры: механизм синхронизации

*Зачем нужны?*

Семафоры — это *флаги или счетчики*, которые контролируют доступ к ресурсу.

Пример с железной дорогой:

* Переезд = общая память.
* Поезда = процессы.
* Семафор = механизм, который разрешает/запрещает проезд.

*Как работает?*

1. Подъехал — *проверил семафор*.
2. Если открыт — *пытаемся закрыть в свою пользу*.
3. После проезда — *открываем обратно*.
    Если не удалось закрыть — *ждем*.

*Спинлоки — плохая идея*

* while (flag != 1) {} — нагружает процессор.
* Постоянный опрос = *высокая нагрузка на CPU*.
* Используется только в ядре ОС или в крайних случаях.
Вместо этого — *семафоры*, которыми управляет ОС.

*API работы с shared memory и семафорами*

*Shared Memory*
----
key_t key = ftok("filename", 1);  // Уникальный ключ
int shmid = shmget(key, size, IPC_CREAT | 0666);  // Создать память
void* ptr = shmat(shmid, NULL, 0);  // Присоединить
shmdt(ptr);  // Отсоединить
shmctl(shmid, IPC_RMID, NULL);  // Удалить
----

*Семафоры*
----
int semid = semget(key, 2, IPC_CREAT | 0666);  // Создание 2 семафоров
semctl(semid, 0, SETVAL, 1);  // Инициализация
semop(semid, &operation, 1);  // Выполнение операции
----

*Операции semop*

* sem_op < 0 — запросить ресурс.
* sem_op > 0 — освободить ресурс.
* sem_op = 0 — ждать, пока значение станет 0.

*Пример флажков:*

* serverLock — сервер блокирует ресурс.
* clientLock — клиент блокирует ресурс.
* turn — чей ход.
* readLast — кто последний работал.


== Сокеты 

=== Введение

*Сокет* — это программный интерфейс, обеспечивающий обмен данными между процессами. В Linux сокеты, как и все остальное, — это файлы. Это значит, что вы взаимодействуете с ними через файловые дескрипторы, используя функции read, write, close и др.
Сокеты часто ассоциируются с сетевыми соединениями, но на самом деле они универсальны: их можно использовать и локально.

*Типы сокетов*
Сокеты классифицируются по:
*Семейству (domain):*

* AF_UNIX — локальные файловые сокеты.
* AF_INET, AF_INET6 — сетевые сокеты.
* AF_PACKET, AF_IPX и др. — специализированные типы.

*Типу передачи (type):*

* SOCK_STREAM — потоковые (надежная передача, аналог TCP).
* SOCK_DGRAM — дейтаграммные (ненадежная передача, аналог UDP).
* SOCK_RAW, SOCK_SEQPACKET — менее распространенные.


=== Пример 1: Файловые сокеты (Unix)
Работа через файловые сокеты — аналог использования именованных каналов (FIFO), но с более мощным интерфейсом.

*Создание сокета:*
----
socket(AF_UNIX, SOCK_DGRAM, 0)
----

*Привязка к файлу:*
----
bind(sockfd, (struct sockaddr *)&addr, addrlen)
----

*Передача и прием:*

----
sendto(), recvfrom() — для отправки и получения данных по адресу.
----
Важно: такие сокеты работают только на одной машине. Даже если файл доступен по сети, соединения не получится.

=== Пример 2: Парные сокеты (socketpair)

Функция *socketpair()* позволяет создать два связанных сокета в памяти. Это альтернатива неименованным каналам (pipe()).

* Работает только в пределах одного процесса (или между процессом и его потомком после fork()).
* Используются для организации двустороннего обмена.
* Пример:
----
int sv[2];
socketpair(AF_UNIX, SOCK_STREAM, 0, sv);
----
*Мнение лектора*
В большинстве случаев неименованные каналы проще и эффективнее. Парные сокеты применяются реже и, по сути, избыточны.

=== Пример 3: Сетевые сокеты (INET)
Самый широко применяемый тип сокетов. Используется для обмена данными между компьютерами по сети.
----
Создание:
socket(AF_INET, SOCK_STREAM, 0) — TCP
socket(AF_INET, SOCK_DGRAM, 0) — UDP

Привязка к порту:
bind(sockfd, (struct sockaddr_in *)&addr, sizeof(addr))

Прослушка соединений:
listen(sockfd, backlog)

Принятие соединения:
accept(sockfd, ...)

Подключение клиента:
connect(sockfd, ...)

Отправка и прием:
read(), write() или recv(), send()

Особенности:
Сервер всегда использует bind(), listen(), accept().
Клиент — connect().
----

=== Практические детали

==== Управление временем ожидания
Сокеты по умолчанию блокируют выполнение:

* read() ждет, пока появятся данные.
* accept() ждет подключений.

Для управления этим используются:
* Флаг O_NONBLOCK
* Системный вызов select() с таймаутами (struct timeval)

==== Порт 33333
В демонстрационном примере использовался учебный порт 33333, который часто бывает свободен.

==== Протокол передачи данных
Чтобы понять, когда данные закончились, важно договориться о формате передаваемой информации:

* Определенный размер пакета.
* Завершающий символ (\n, \0).
* Контрольная сумма (CRC).
* Фиксированный формат (заголовок, тело, хвост).

Иначе вы не сможете различить просто паузу и конец сообщения.

==== Взаимодействие с Telnet

Лектор показал, как подключаться к серверу через telnet:
* telnet 127.0.0.1 33333 — простой способ протестировать работу сервера.
* Отправка сообщений в виде строк.

==== Особенности очистки
После завершения работы сервера:

* Порт остается занятым несколько секунд.
* Чтобы порт освобождался сразу, необходимо использовать флаг SO_REUSEADDR при создании сокета (через setsockopt()).

== Сигналы

Сигналы в Linux — это механизм межпроцессного взаимодействия, суть которого сводится к тому, что ОС передаёт определённые короткие сообщения (сигналы) процессу.

=== Ключевые особенности сигналов:

Обработка сигнала происходит либо немедленно, либо не происходит вообще (если игнорируется);

==== Сигнал может быть:

* Обработан (через функцию-обработчик);
* Игнорирован;
* Обработан по умолчанию ОС (например, завершение процесса);
* При этом выполнение кода может продолжаться с места, на котором было прервано.

==== Игнорирование и блокировка сигналов

*Игнорирование* — сигнал уничтожается, программа его «не замечает»;

*Блокировка* — сигнал сохраняется, но не обрабатывается до снятия блокировки.
Сигналы можно блокировать через системные вызовы. При этом можно узнать, что сигнал был получен, но реакция произойдёт только при разблокировке.

Некоторые сигналы нельзя игнорировать или блокировать:

* `SIGKILL` (9) — аварийное завершение процесса;
* `SIGSTOP` (19) — остановка процесса.

==== Популярные сигналы

* `SIGINT` — Ctrl+C в терминале, прерывает выполнение;
* `SIGHUP` (1) — «повесить трубку», сигнал перезапуска/перечитывания конфигурации;
* `SIGCHLD` — завершение дочернего процесса;
* `SIGUSR1` и `SIGUSR2`` — пользовательские сигналы (номера ~10–12), могут использоваться для кастомных реакций.

*Использовать пользовательские сигналы для бизнес-логики не рекомендуется.*

=== Работа с сигналами в C
Мы можем:

* Назначить обработчик с помощью sigaction();
* Заблокировать/разблокировать сигнал с помощью sigprocmask();
* Использовать sigwait(); для «усыпления» до прихода сигнала.

*Важно: обработчики должны быть реентерабельны — не использовать глобальные переменные без синхронизации. printf() в обработчике — плохая идея.* 


==== Устаревшие и современные подходы
Раньше использовался массив sys_siglist для описаний сигналов. Сейчас — strsignal() (функция);
Примеры адаптированы под новые стандарты (2024+);
Linux активно обновляется, старые конструкции могут не работать.

==== Практические примеры

Программа SIGDEMO:

* Обрабатывает сигнал SIGTERM через TermHandler() — выводит сообщение и завершает работу;
* Блокирует сигнал SIGHUP, который не вызывает реакции без снятия блокировки.

Программа с sigwait():

* Блокирует сигнал SIGHUP, а затем «ждёт» его через sigwait() — нагрузка на CPU отсутствует, программа просыпается только при получении сигнала.

=== Рассылка и генерация сигналов

Сигналы можно подавать вручную через kill и raise():

* kill(pid, signal) — посылает сигнал другому процессу;
* raise(signal) — подаёт сигнал самому себе.

*Поведение PID в kill:*

* > 1 — сигнал конкретному процессу;
* 0 — всем из текущей группы;
* < 0 — всем из указанной группы по модулю;
* -1 — всем процессам в системе (аккуратно!).

*Сигналы — мощный, но технический инструмент. Их основное назначение — управление процессом: аварийное завершение, мягкое завершение, перезапуск, реакция на системные события.*
